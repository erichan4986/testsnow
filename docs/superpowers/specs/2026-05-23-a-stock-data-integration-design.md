# A-Stock Data Integration Design

## 1. 目标与范围

将现有雪球舆情监控系统升级为多维度 A 股分析工具，以**圣邦股份**为试点，整合技术指标、研报、公告、资金流向、个股新闻等数据源，通过 FinancialAgent（Kimi API）进行跨源深度分析，并以 Obsidian 知识库形式沉淀可复用的研究原子笔记。

**本期范围**：
- 6 只持仓股票全部纳入（以圣邦股份为深度试点）
- 新增 5 类数据源
- 新建项目内 Obsidian vault 作为知识层
- 个股报告新增 4 个分析板块
- **周期性报告生成框架**：支持基于历史周报自动生成季报（3月）、半年报（6月）、年报（12月）

**不在本期**：
- 知乎 API / iWencai API（用户计划二期加入）
- 自动化定时采集（仍保持每周手动触发）
- 跨股票对比组合分析

## 2. 数据收集层扩展

在现有雪球/东财股吧帖子数据基础上，每只 A 股股票新增以下数据源：

| 数据类别 | 具体指标/内容 | 数据来源 | 优先级 |
|---------|-------------|---------|-------|
| **技术指标** | MACD, RSI, KDJ, MA(5/10/20/60), 布林带 | mootdx K线 + stockstats | P0 |
| **最新研报** | 近4个月券商研报标题、评级、目标价、核心观点 | 东财 reportapi / akshare | P0 |
| **公司公告** | 近3个月定期报告、重大事项、股东变动 | 巨潮 cninfo | P0 |
| **资金流向** | 主力净流入、散户净流入、大单占比 | 百度股市通 / akshare | P1 |
| **个股新闻** | 近1个月相关新闻标题+摘要 | akshare | P1 |
| **估值数据** | PE/PB/市值/换手率（已有腾讯接口） | 腾讯财经 | 已有 |
| **一致预期** | 未来3年 EPS/BPS 一致预期（已有） | 东财 / akshare | 已有 |

### 2.1 技术指标采集方案

```python
# mootdx 获取日线数据
from mootdx.quotes import Quotes
client = Quotes.factory(market='std')
kline = client.kline(code='300661', market=0, category=4)  # 0=深圳, 4=日线

# stockstats 计算指标
import stockstats
ss = stockstats.StockDataFrame.retype(kline)
macd = ss['macd']           # MACD line
rsi = ss['rsi_14']          # RSI 14日
kdj_k = ss['kdjk']          # KDJ K值
ma5 = ss['close_5_sma']     # 5日均线
boll_upper = ss['boll_ub']  # 布林带上轨
```

采集周期：最近 120 个交易日（约半年），用于计算所有中长期指标。

### 2.2 研报采集方案

主接口：`ak.stock_profit_forecast_ths(symbol="300661")` 获取一致预期
备选接口：东财 reportapi（直接 HTTP）获取研报列表，含标题、机构、评级、目标价

采集规则：
- 时间范围：近 4 个月
- 每只股票最多取 20 篇
- 字段：标题、机构、作者、评级、目标价、摘要、发布日期、链接

### 2.3 公告采集方案

接口：巨潮资讯网 cninfo API
- `ak.stock_notice_report()` 或直接 HTTP 请求
- 时间范围：近 3 个月
- 类型过滤：定期报告、重大事项、股权激励、增减持、并购
- 每只股票最多取 15 条

code: "300661"
date: "2025-05-23"
category: 技术指标
data_source: mootdx + stockstats
valid_until: "2025-06-06"     # 数据有效期，技术类较短
confidence: 确认事实          # 三层认知标注：确认事实 / 我推断 / 我认为
tags: [技术指标, MACD, 圣邦股份]

# 圣邦股份 - 20250523 技术指标

## 原始数据
- 收盘价: 89.50
- MACD: DIF=-0.12, DEA=-0.08, MACD柱状=-0.08

## 5. FinancialAgent 设计

### 5.1 定位与职责

FinancialAgent 是一个**跨数据源深度分析器**，职责：
1. 读取某只股票的所有原子笔记（技术面、研报、公告、资金、舆情）
2. 调用 Kimi API 进行跨源关联分析
3. 输出结构化分析结果，写入 `2025MMDD-深度分析.md`
4. 在原子笔记中填充 `analysis` 字段

### 5.2 分析框架（Prompt 设计）

```
你是一位专业的半导体行业研究员，正在分析股票 {stock_name}（{code}）。

## 输入数据
以下是从多个数据源采集的原始信息，已按类别整理：

[1. 技术面数据]
{technical_data}

[2. 最新研报摘要]
{report_data}

[3. 近期公告]
{announcement_data}

[4. 资金流向]
{fundflow_data}

[5. 个股新闻]
{news_data}

[6. 社区舆情]
{sentiment_data}

## 分析任务
请按以下框架输出分析，每条判断必须标注认知层级：

### A. 确认事实（基于公告、研报、财报的明确信息）
- 列出 3-5 条不可辩驳的事实

### B. 我推断（基于多源交叉的合理推论，需说明依据）
- 技术面与基本面的共振/背离
- 资金流向与舆情的验证/矛盾
- 机构评级与当前股价的偏离

### C. 我认为（基于推理的主观判断，需明确假设前提）
- 短期（1-4周）走势判断
- 中期（1-3个月）关键催化/风险
- 仓位建议（加仓/持有/减仓/观望）

## 输出格式
必须返回纯 JSON，包含：
{
  "confirmed_facts": ["事实1", "事实2"],
  "inferences": [{"claim": "推断", "basis": "依据", "confidence": 0.8}],
  "opinions": [{"claim": "观点", "assumptions": ["假设1"], "timeframe": "短期"}],
  "key_risks": ["风险1"],
  "catalysts": ["催化1"],
  "position_suggestion": "持有",
  "report_sections": {
    "technical_analysis": "用于报告 Section 3 的 Markdown 文本",
    "report_summary": "用于报告 Section 4 的机构共识文本",
    "announcement_signals": "用于报告 Section 5 的公告信号文本",
    "fundflow_interpretation": "用于报告 Section 6 的资金解读文本"
  }
}
```

### 5.3 三层认知标注规则

| 层级 | 含义 | 使用场景 | 示例 |
|------|------|---------|------|
| **确认事实** | 有原始数据直接支撑，无需推理 | 公告内容、财报数据、研报评级 | "Q1净利润同比增长31%" |
| **我推断** | 多源交叉后的合理推论，有依据但非确定性结论 | 技术面与基本面共振、资金流向解读 | "主力近5日净流入3500万，推断机构在低位吸筹" |
| **我认为** | 基于推理的主观判断，依赖假设前提 | 走势预测、仓位建议 | "若突破95元阻力，我认为中期可看110元" |

### 5.4 与报告层的接口

FinancialAgent 输出后，通过以下方式进入报告：
1. 写入 `knowledge/<股票>/2025MMDD-深度分析.md`
2. `stock_reporter.py` 读取该文件的 `report_sections` 字段
3. 直接嵌入到 Markdown 报告的对应 Section

### 6.2 错误处理与降级策略

| 故障场景 | 处理策略 | 降级输出 |
|---------|---------|---------|
| mootdx 连接失败 | 尝试 akshare 备选接口获取 K线 | 标注"数据暂缺"，跳过技术板块 |
| 东财研报 API 限流 | 使用本地缓存（7天内有效） | 标注"沿用上期研报数据" |
| 巨潮公告 API 超时 | 缩短时间范围（3个月→1个月）重试 | 只显示近1个月公告 |
| Kimi API 超时(60s) | 回退到规则摘要（关键词提取+排序） | 标注"AI分析暂缺，以下为规则摘要" |
| 单数据源全部失败 | 继续用其他数据源生成报告 | 报告中对应 Section 显示"本期数据暂缺" |

### 6.3 数据新鲜度管理

`data_registry.json` 记录每条数据的元信息：

```json
{
  "300661": {
    "technical": {
      "source": "mootdx",
      "fetched_at": "2025-05-23T10:00:00",
      "valid_until": "2025-05-24T00:00:00",
      "path": "data/raw/20250523/technical_300661.json"
    },
    "reports": {
      "source": "eastmoney_reportapi",
      "fetched_at": "2025-05-23T10:05:00",
      "valid_until": "2025-08-23T00:00:00",
      "path": "data/raw/20250523/reports_300661.json"
    }
  }
}
```

- **技术数据**：有效期 1 天（价格每日变化）
- **研报数据**：有效期 90 天（研报发布频率低）
- **公告数据**：有效期 30 天
- **舆情数据**：有效期 7 天

采集时优先检查 registry，未过期数据直接复用，减少 API 调用。

## 11. 周期性报告生成（季报 / 半年报 / 年报）

### 11.1 设计目标

每周生成的报告和原子笔记作为"原始素材"，系统支持按时间窗口聚合生成更高层次的周期性报告：
- **季报**：聚合近 13 周（约3个月）的周报
- **半年报**：聚合近 26 周（约6个月）的周报
- **年报**：聚合近 52 周（约12个月）的周报

### 11.2 触发方式

手动触发，而非自动：
```bash
python scripts/generate_periodic_report.py --type quarterly --year 2025 --quarter 2
python scripts/generate_periodic_report.py --type semiannual --year 2025 --half 1
python scripts/generate_periodic_report.py --type annual --year 2025
```

### 11.3 数据源（部分重新采集，匹配时间跨度）

周期性报告不是简单聚合周报，而是**按时间跨度重新采集关键数据**，同时复用历史周报中的分析结论：

| 数据类别 | 处理方式 | 时间跨度匹配 | 说明 |
|---------|---------|-------------|------|
| **季度/年度财报** | **重新采集** | 季报取当季财报，半年报取半年财报，年报取年度财报 | 周报只含片段，必须重新拉取完整财报 |
| **技术指标** | **重新采集** | 季报看MA60，半年报看MA120，年报看MA250 | 重新拉取对应周期K线，计算匹配时间跨度的指标 |
| **研报** | 复用 + 过滤 | 周期内发布的研报 | 从周报中聚合，但过滤对应时间范围 |
| **公告** | 复用 + 过滤 | 周期内的重大事项 | 同上 |
| **舆情** | 复用 + 聚合 | 周期内的舆情变化趋势 | 聚合多篇周报，提取情绪变化曲线 |
| **历史深度分析** | 复用 | 周期内每周的分析结论 | 用于判断回顾和主题演变 |

**重新采集的指标要求：**

| 报告类型 | K线周期 | 关键均线 | 其他指标 |
|---------|---------|---------|---------|
| **季报（3个月）** | 60个交易日 | MA20, MA60 | MACD, RSI, KDJ, 布林带 |
| **半年报（6个月）** | 120个交易日 | MA60, MA120 | MACD, RSI, KDJ, 布林带, 波动率 |
| **年报（12个月）** | 250个交易日 | MA120, MA250 | MACD, RSI, KDJ, 布林带, 年线趋势 |

`weekly_index.json` 结构（用于定位历史周报）：
```json
{
  "300661": [
    {"date": "2025-05-23", "note_path": "knowledge/圣邦股份/20250523-深度分析.md", "report_path": "reports/2025-05-23/圣邦股份.md"},
    {"date": "2025-05-16", "note_path": "knowledge/圣邦股份/20250516-深度分析.md", "report_path": "reports/2025-05-16/圣邦股份.md"}
  ]
}
```

### 11.4 聚合分析逻辑

`periodic_reporter.py` 执行以下步骤：

1. **重新采集周期数据**：
   - 调用 `data_collector` 拉取匹配时间跨度的 K线数据（60/120/250日）
   - 调用 `data_collector` 拉取对应周期的财报数据（季报/半年报/年报）
   - 重新计算技术指标（MA60/120/250, MACD, RSI 等）

2. **收集历史分析**：根据时间窗口，从 `weekly_index.json` 读取该股票的历史 `深度分析.md`

3. **提取**：从每篇深度分析中提取以下结构化字段：
   - `confirmed_facts`（确认事实）
   - `inferences`（我推断）
   - `opinions`（我认为）
   - `position_suggestion`（仓位建议）
   - `key_risks`（风险）
   - `catalysts`（催化）

4. **汇总**：调用 Kimi API，输入"重新采集的周期数据 + 多期历史分析结论"，生成周期性视角的复盘分析

### 11.5 Kimi Prompt 设计（周期性分析）

```
你是一位投资组合经理，正在复盘股票 {stock_name}（{code}）的 {period_type} 表现。

## 输入 1：该 {period_type} 的完整周期数据（已匹配时间跨度）

[1. 周期技术指标]
- 时间跨度: {period_span} 个交易日
- MA60: {value}, MA120: {value}, MA250: {value}（根据报告类型展示对应均线）
- 周期内MACD走势: ...
- 周期内RSI区间: ...
- 周期最高价/最低价/涨跌幅: ...

[2. 周期财报数据]
- 报告期: {report_period}
- 营业收入: {value}（同比/环比）
- 归母净利润: {value}（同比/环比）
- 毛利率/净利率变化: ...
- 关键财务指标: ROE, 资产负债率, 经营现金流等

[3. 周期内研报共识变化]
- 期初一致预期 EPS: {value}
- 期末一致预期 EPS: {value}
- 评级变化: ...

## 输入 2：该周期内 {n} 周的连续深度分析记录

{依次列出每周的 confirmed_facts, inferences, opinions, position_suggestion}

## 分析任务

请输出一份 {period_type} 复盘报告，结构如下：

### 1. 周期事实盘点（Period Facts）
- 该周期内最确定的事实（基于完整财报 + 技术指标验证）
- 财报数据揭示的经营趋势（vs 市场预期的偏差）
- 技术面给出的周期级别信号（年线/半年线位置、趋势方向）

### 2. 事实演变（Fact Evolution）
- 哪些事实在周期内发生了变化？（如业绩预期上调/下调）
- 哪些事实始终未变？（如行业地位、竞争格局）

### 3. 判断回顾（Judgment Review）
- 回顾每周的"我认为"，哪些判断被验证了？哪些被证伪了？
- 按时间线列出仓位建议的变化，分析背后的逻辑转变
- **特别关注**：周报中的短期判断与周期级别事实的偏差

### 4. 关键主题（Key Themes）
- 整个周期内反复出现的话题/催化/风险是什么？
- 这些主题的权重如何变化？

### 5. 周期性结论（Period Conclusion）
- **确认事实**：经过完整周期验证后，最确定的事实
- **我推断**：基于财报趋势 + 技术趋势的综合推论
- **我认为**：基于上述分析，对下个周期的判断和仓位建议

### 6. 经验教训（Lessons）
- 周报框架在捕捉周期级机会/风险上的盲点
- 如果有时光机，在周期起点会做出什么不同决策？

## 输出格式
返回纯 JSON：
{
  "period_facts": [{"fact": "事实", "evidence": "财报/技术指标依据"}],
  "fact_evolution": [{"fact": "事实", "change": "如何变化", "weeks": ["2025-05-23", "2025-05-16"]}],
  "judgment_review": [{"week": "2025-05-23", "claim": "判断", "outcome": "验证/证伪", "reason": "原因"}],
  "key_themes": [{"theme": "主题", "mentions": 5, "trend": "上升/下降/持平"}],
  "period_conclusion": {"confirmed_facts": [], "inferences": [], "opinions": [], "position_suggestion": "持有"},
  "lessons": ["教训1"],
  "report_markdown": "完整的 Markdown 格式报告"
}
```

## 10. 关键设计决策

1. **为什么用项目内 Obsidian vault 而非外部笔记软件？**
   - 保证数据与研究过程可版本控制（git）
   - 不依赖特定软件，Markdown 是通用格式
   - 用户可在本地用 Obsidian 打开获得图谱/链接功能

2. **为什么 FinancialAgent 单独成模块而非扩展 KimiAnalyzer？**
   - KimiAnalyzer 负责单源（舆情）分析，FinancialAgent 负责跨源关联
   - 两者 Prompt 和输出结构完全不同，解耦便于独立迭代

3. **为什么 data_registry 用 JSON 而非数据库？**
   - 保持项目轻量，无需引入 SQLite/PostgreSQL
   - JSON 可读可 diff，便于 git 追踪变更
   - 数据量小（6只股票 × 5数据源），JSON 完全够用

4. **为什么周期性报告不自动触发，而是手动？**
   - 季报/半年报/年报的生成时机需要人工判断（如财报季后复盘更有意义）
   - 避免 API 调用浪费（聚合 52 周数据 token 消耗大）
   - 生成结果建议人工审阅后再归档
